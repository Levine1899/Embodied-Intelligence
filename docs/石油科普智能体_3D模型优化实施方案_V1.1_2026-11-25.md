## 0. 修订结论与实施原则

### 0.1 V1.1 修订结论

V1.0 的总体路线保留：**不推倒重做现有三维世界，先建立稳定资产语义和工艺连接，再修现有模型逻辑，随后统一 GLB 加载，最后扩展储罐、泵组、产品资产并做全局视觉与性能优化。**

V1.1 将 V1.0 中未闭合的工程约束补齐，尤其是：

1. 资产身份不再依赖节点名称；新增持久化 `nodeUid`，并定义 Blender 自定义属性、glTF `extras`、Manifest 的一致性规则。
2. 工艺连接明确坐标空间、单位、资产根变换和端点锚点解析规则。
3. `web/data/process-connections.json` 是连接拓扑与路径控制点的唯一权威数据源；Blender 构建和前端渲染都读取它，不允许各自另写路线坐标。
4. 工艺依据建立版本和审批门禁；未审核路径不得作为已确认工艺事实发布。
5. M0/M1 细分为可验证的垂直切片，不再要求一次录入全部环节连接。
6. GLB 加载器固定采用本地 `esbuild` 构建路线；Three.js 版本必须先与当前运行库核实，再精确锁定，不能盲目新增第二套 THREE runtime。
7. 细节等级与结构剖切状态分离；不再用 LOD 数字承担结构状态。
8. 性能指标区分资源计数、资产字节估算和真实设备侧 GPU/显存观测。
9. E2E 统一采用 Playwright；Schema、Manifest、连接与导出一致性纳入 CI。
10. L3 任务业务条件与模型功能验收分离，保护当前 70% 完成规则及每次进入重置逻辑。

### 0.2 本轮不可妥协的原则

- 工艺正确性优先于画面复杂度；没有已批准依据，不补画真实物流。
- Blender、GLB、Manifest、前端和 AI 上下文使用同一组稳定 ID。
- 实体管线、教学高亮线和粒子动画共用连接拓扑、端点和中心线数据。
- 不用透明完整外壳伪装真实半剖。
- 不以截图代替结构断言，也不以 CI 虚拟 GPU 代替目标设备性能实测。
- 每个阶段先形成可复现基线，再进行有限范围改造；阶段失败先修复，不跨阶段叠加未验证改动。
- 不允许 Harness 在未声明的情况下重写任务规则、知识文案、问答逻辑、语音链路或无关 UI。

### 0.3 明确不做

- 不把教学模型包装成工程设计、设备选型、机械强度或 CFD 仿真模型。
- 不为画面“更像炼厂”而任意增加未审核的设备和管线。
- 不一次性重建 L1–L5 全部资产。
- 不一次性把所有 OBJ 迁移为 GLB。
- 不在资产语义和连接数据未闭环前先做全局 HDR、后处理和高成本阴影。
- 不用 `renderer.info.memory.geometries/textures` 冒充实际 GPU 显存字节数。

## 2. 统一资产身份与 Manifest 契约

### 2.1 ID 职责

| 字段 | 职责 | 唯一性范围 | 示例 |
|---|---|---|---|
| `assetId` | 可发布模型资产包 | 全项目唯一 | `distillation_unit_hero` |
| `systemId` | 工艺/设备子系统 | 全项目唯一 | `atmospheric_overhead` |
| `objectId` | 前端可交互逻辑设备 | 全项目唯一 | `overhead_condenser` |
| `semanticId` | 模型内部可识别部件 | 按 `assetId` 命名空间唯一 | `condenser_shell` |
| `nodeUid` | GLB/Blender 节点稳定主键 | 每个 asset 内唯一，不随导出重建变化 | UUIDv5 或持久化 UUID |
| `anchorId` | 管口/设备端口/空间锚点 | 按 asset 唯一 | `condenser_vapor_inlet` |
| `connectionId` | 工艺连接或教学连接 | 全工艺图唯一 | `atm_overhead_to_condenser` |

`systemId` 用于系统级分组，`objectId` 用于设备选择和业务上下文，`semanticId` 用于内部部件说明/高亮，`nodeUid` 用于映射实际 glTF node，`anchorId` 用于空间连接，`connectionId` 用于物流路径。不得混用。

### 2.2 `nodeUid` 稳定性规则

**禁止把 `node.name` 作为节点唯一主键。** glTF `name` 是可选的应用显示字段，不保证唯一；它只用于人类阅读和调试。

身份来源分三层：

1. **Blender 自定义属性是建模/生成时的身份源**：对象保存 `petro.nodeUid`、`petro.assetId`、`petro.systemId`、`petro.objectId`、`petro.semanticId`、`petro.role`。
2. **导出 glTF node `extras` 携带核心身份副本**：用于模型离开 Blender 后仍可定位节点。
3. **Manifest 是发布时的机器索引**：由构建/导出检查器生成，不由开发人员手动维护同一份字段的第二套值。

`nodeUid` 生成规则：

- 手工资产：创建时生成一次并写入 `.blend` 自定义属性；以后改名、移动、调整网格不能重新生成。
- 程序化资产：用固定项目 namespace + 稳定语义路径生成 UUIDv5，语义路径必须包含设备、部件和必要的实例标识，不能使用循环序号、对象创建顺序或随机数。
- 复制节点时必须为新节点分配新 ID；构建检查器检测重复即失败。
- 删除节点后不复用旧 ID；节点迁移/合并要生成可审计的映射记录。

### 2.3 Blender / glTF / Manifest 一致性

glTF `extras` 核心字段建议：

```json
{
  "extras": {
    "petro": {
      "nodeUid": "<stable-uuid>",
      "assetId": "distillation_unit_hero",
      "systemId": "atmospheric_overhead",
      "objectId": "overhead_condenser",
      "semanticId": "condenser_shell",
      "role": "pressure_vessel_shell"
    }
  }
}
```

约束：

- 这些字段从 Blender 自定义属性导出；不允许分别手工维护 extras 和 Manifest。
- Manifest 由 GLB 导出结果和 Blender 构建元数据生成。
- 校验器必须逐节点比对 `nodeUid`、`objectId`、`systemId`、`semanticId`、`role`。
- 导出后 extras 丢失、ID 重复、Manifest 引用不存在节点、实际节点未登记且未标记 support，均视为构建失败。

### 2.4 Manifest 结构要求

正式文件：`schemas/asset-manifest.schema.json`（JSON Schema Draft 2020-12）。校验器建议使用 Node.js + AJV；如果项目已有兼容的 Schema 工具，应先评估再决定，禁止再造一个不完整的手写 JSON 校验器。

每个 `*.manifest.json` 至少包含：

- `schemaVersion`、`assetId`、`assetVersion`、`build`、`source`；
- `runtime.format`、GLB URI、SHA-256、文件大小；
- `coordinateSystem`、`bounds`，并注明 bounds 所属坐标系；
- `systems[]`、`objects[]`、`nodes[]`、`anchors[]`；
- `representations`：overview/detail/closeup 对应节点集；
- `structureModes`：external/half/full/ghost 各状态的显示/隐藏/透明/裁切节点规则；
- `dynamicBindings`：液面、浮盘、阀轮、流体粒子等动态节点/参数绑定；
- `nonInteractiveSupport[]`：不允许交互但需要保留的支撑/平台/栏杆/基础对象；
- `processBasis[]`、`limitations[]`、第三方素材许可信息。

**细节等级与结构模式必须分开。** 示例：`detailLevel="closeup"` 可以同时搭配 `structureMode="half"`，二者不能共用一个数字 `level`。

建议的数据结构示意：

```json
{

  "assetVersion": "<generated-from-content-hash>",

    "blenderVersion": "<actual-version>",
    "exporterVersion": "<actual-version>",
    "exportOptionsHash": "<generated-hash>"
  },
  "runtime": {
    "format": "glb",
    "uri": "<content-hashed-file>",
    "sha256": "<generated-sha256>",
    "bytes": 0
  },
  "systems": [],
  "objects": [],
  "nodes": [],
  "anchors": [],
  "representations": {
    "overview": [],
    "detail": [],
    "closeup": []
  },
  "structureModes": {
    "external": { "show": [], "hide": [], "ghost": [] },
    "half": { "show": [], "hide": [], "ghost": [] },
    "full": { "show": [], "hide": [], "ghost": [] },
```

以上仅定义形状，不得将空数组或占位值当作真实模型数据。

### 2.5 坐标系契约

坐标定义必须明确到来源和目标：

- Blender 源场景默认 Z-up；项目内现有 `make_tower.py` 已注释其网页坐标映射，不能假定所有历史脚本都一致。
- glTF 运行坐标采用右手坐标系、`+Y` 向上、线性单位米；导出时的轴变换必须记录和验证。
- Manifest 中的 `bounds`、`anchors` 和 connection waypoints 必须标注坐标空间。
- 每个 GLB root 定义唯一 `assetLocal` 原点；运行时通过 `assetRoot.matrixWorld` 统一转换到世界坐标。
- 禁止在 L2/L3/L4 各自硬编码同一连接的额外旋转、缩放或偏移。
- `coordinateSpaceId` 必须引用已登记空间；不允许无上下文的裸 XYZ。

坐标变换链统一为：

`Blender source -> glTF assetLocal -> assetRoot -> levelRoot -> world`

转换只能在边界处执行一次。前端路径点在 `assetLocal` 中保存，运行时使用同一个 `assetRoot` 世界矩阵变换。

## 3. 工艺连接数据：唯一权威来源

### 3.1 唯一数据文件

正式文件：`web/data/process-connections.json`。

选择 `web/data/` 是为了前端可按现有静态资源路径读取；Blender 构建脚本从仓库根目录解析该路径。无论 Blender 和前端在哪里执行，都必须读取仓库中同一份文件，禁止复制出 `tools/process-connections.json`、`web/levels/l4-paths.json` 等第二份路线定义。

该文件负责：连接拓扑、from/to 锚点引用、介质和相态、路径中间控制点、展示策略、工艺依据和审核状态。

Manifest/GLB 负责：设备和端口锚点的身份、锚点实际变换、资产层级。

因此连接路径由以下内容组成：

`from.anchor transform + JSON waypoints + to.anchor transform`

JSON 不重复保存端点绝对坐标，避免端口移动后路径端点和模型不一致。路径控制点只保存中间 `waypoints`。

### 3.2 Connection Schema 示例

```json
{
  "schemaVersion": "1.0.0",
  "coordinateSpaces": [
    {
      "coordinateSpaceId": "distillation_unit_asset_local",
      "type": "assetLocal",
      "assetId": "distillation_unit_hero",
      "unit": "meter",
      "basis": "gltf-right-handed-y-up"
    }
  ],
  "connections": [
    {
      "connectionId": "atm_overhead_to_condenser",
      "from": {
        "objectId": "atmospheric_tower",
        "anchorId": "atm_tower_top_vapor_outlet"
      },
      "to": {
        "objectId": "overhead_condenser",
        "anchorId": "condenser_vapor_inlet"
      },
      "coordinateSpaceId": "distillation_unit_asset_local",
      "waypoints": [[0, 0, 0]],
      "medium": "overhead_vapor",
      "phase": "gas",
      "direction": "from-to",
      "displayColorToken": "stream-vapor",
      "display": {
        "overview": true,
        "detail": true,
        "particles": true
      },
      "teachingSimplification": true,
      "basis": {
        "basisId": "<approved-basis-id>",
        "version": "<basis-version>",

        "sourceOrg": "<source-organization>",

```

示例路径只说明字段，不表示任何具体工艺关系已获批准。不得复制占位连接到生产清单。

### 3.3 工艺依据与发布门禁

每条关键连接必须提供：

- `basisId`、`version`、`sourceTitle`、`sourceOrg`、`sourceUrlOrDoc`、`sourceSection`；
- `scope`：明确适用哪一套教学简化流程；
- `limitations`：省略的设备、物流、控制系统和边界；
- `reviewStatus`：`draft / reviewed / approved / rejected`；
- `reviewedBy`、`reviewedAt`（已审核时必填）。

发布规则：

- `approved`：允许作为正式流程内容发布。
- `draft` / `reviewed`：只允许开发预览；前端必须标记“待工艺审核/教学示意”，不得当作已确认事实。
- `rejected`：禁止渲染为正式流程；构建失败或进入明确的禁用状态。
- 不存在依据的连接不得由 AI 或代码生成器自行补全。缺少依据时登记为 `pendingBasis`，并阻断该连接的生产发布。

### 3.4 唯一数据源职责

| 模块 | 唯一职责 | 禁止行为 |
|---|---|---|
| `process-connections.json` | 连接 ID、端点引用、拓扑、waypoints、介质、方向、依据 | 不存私有动画算法，不重复端点坐标 |
| Blender builder | 读取连接 JSON 和 Blender anchor，生成实体管线；输出前做端点校验 | 不手写第二套工艺路径，不凭经验补管 |
| GLB/Manifest | 导出 anchor 节点、稳定 ID 和资产变换 | 不在 Manifest 里重新定义另一套连接中心线 |
| ConnectionRenderer | 按连接 ID 和同一 waypoints 生成教学显示线 | 不硬编码路径坐标 |
| FlowAnimator | 沿同一个连接路径驱动粒子/箭头 | 不自行创建偏离实体管线的 CatmullRom 控制点 |
| 总览/近景/独立塔页 | 使用同一 `connectionId`，应用各自显示策略 | 不为同一连接定义不同拓扑和端点 |
| AI 场景上下文 | 引用 `connectionId`、`objectId`、`medium`、审核状态 | 不只按屏幕文字推断物流关系 |

如需要将教学高亮线与真实实体管线分开以避免遮挡，只允许使用显式 `displayOffset` 或 `renderOffset`，不得改变工艺拓扑、端点和物质方向，并需标记为显示偏移。

### 3.5 坐标与连接校验

- from/to anchor 必须在对应 Manifest/GLB 中存在。
- `coordinateSpaceId` 必须存在，且 assetId 与两端资产/系统关系匹配。
- Blender builder 用真实 anchor 世界矩阵 + waypoints 构建实体管线。
- 前端用相同 anchor matrix + waypoints 生成显示线和粒子曲线。
- 自动校验端点位置误差、方向向量误差、缺失 anchor、重复 connectionId、非法介质、依据状态和管段断裂。
- 容差应配置在 Schema/项目配置中，按场景单位校准；初次试点可用 0.05 m 位置误差、5° 方向误差作为候选值，但必须在真实模型尺度下确认，未确认前不得写成已通过。
- 修改一个 waypoint 后，Blender 实体管线与前端路线必须同步变化，这是单一数据源的强制验收，不得仅靠端点恰好重合来证明。

A. 任务业务 E2E：达到 70% 就完成；不启动泵送也通过；不要求必须观察两个罐型。  
B. 模型状态 E2E：液面随滑块变化；固定顶不动；外浮顶浮盘贴合液面；两种罐状态不串。  
C. 可选功能 E2E：泵送启停/暂停/重播、粒子沿 connection 运行、端点与总览路线一致。  
D. 重进/重置 E2E：每次进入恢复 2% 和默认状态，任务状态与关卡状态一致。

## 5. GLB 统一 Loader 与构建体系

### 5.1 技术决策

- 正式模型格式：GLB/glTF 2.0。
- 兼容格式：OBJ/MTL 仅作为迁移期回退；最终逐资产移除重复解析实现。
- 打包工具：采用 **esbuild**，不同时引入 Vite 作为第二套构建系统。
- 依赖：执行前从现有 `web/assets/three.browser.js` 的 `THREE.REVISION` 核实实际版本；若为 r180，对应 npm 包应精确锁定为与其一致的版本（通常为 `three@0.180.0`，但以实测版本和运行时比对为准）。不得使用 `^`、`~` 或 `0.180.x` 模糊范围。
- lockfile 必须提交；构建产物随站点本地部署，不依赖 CDN。

### 5.2 单一 THREE Runtime

当前页面通过经典脚本注入 `window.THREE`。迁移时：

1. 新建一个 ES Module 入口，导入同版本 `three` 和 `GLTFLoader`。
2. 用 esbuild 构建为页面可加载的单一本地 bundle，挂载 `window.THREE` 和 `window.GLTFLoader`。
3. 更新 HTML 加载入口，删除旧 `three.browser.js` 的重复加载；禁止同时加载两个 THREE runtime。
4. 运行时检查 `THREE.REVISION`；Loader 和 THREE 必须使用同一模块实例。
5. 先用一个资产试点并保留 OBJ fallback，完成验证后再迁移其他资产。
6. 不允许在页面中额外从 CDN 或动态网络加载不同版本的 Three.js/decoder。

### 5.3 ModelLoader API

建议统一接口：

```js
const handle = await ModelLoader.load({
  assetId: 'separator_hero',
  url: 'assets/models/separator_hero/<content-hash>.glb',
  manifestUrl: 'assets/models/separator_hero/manifest.json',
  fallback: {
    format: 'obj',
    obj: 'assets/separator/separator.obj',
    mtl: 'assets/separator/separator.mtl'
  }
});
```

返回至少包括：

- `root`、`nodesByUid`、`nodesBySemanticId`、`objectsByObjectId`、`systemsBySystemId`、`anchorsByAnchorId`；
- `assetId`、`assetVersion`、`manifest`、`loadWarnings`；
- `animations`、`dispose()`。

Loader 必须处理：Promise 错误、进度、Manifest 校验、GLB hash/版本匹配、extras 映射、fallback 提示、资源所有权和释放。

### 5.4 压缩策略

- 首轮先用未压缩 GLB 完成正确性试点。
- 几何体达到体积瓶颈后评估 Meshopt 或 Draco，按实际解码耗时和下载收益选择一种主路径。
- 存在贴图且体积/显存有收益时才评估 KTX2/BasisU。
- 所有 decoder/transcoder 本地部署、精确锁版并纳入 hash/测试。
- 不为纯几何体资产引入没有收益的额外解码链。

### 5.5 内容哈希和缓存

- GLB 文件名采用内容 hash 或构建生成的不可变版本。
- Manifest 引用具体 hash 文件；HTML/JS 入口只引用对应 Manifest。
- 禁止散落手工 `?v=08`、日期串或随意递增版本参数。
- 总览、L4、`tower.html` 对同一 assetId 必须加载相同 assetVersion。
- 回滚以 Manifest 指针回滚，不覆盖历史不可变 GLB。

## 6. PBR、镜头与视觉规范

### 6.1 材质库

先建立项目共享材质 token，而不是每个模型独立调色。基础类别包括涂装碳钢、不锈钢、镀锌钢、保温管、混凝土、砂岩/泥岩、油、水、气相示意材质。所有材质要在统一灯光和曝光下验证，避免金属过度镜面或材质发光掩盖结构。

### 6.2 纹理规范

- Base Color 使用 sRGB；Roughness/Metalness/Normal/AO 按非颜色数据处理。
- 贴图必须有来源/许可记录。
- 近景优先 UV 质量；不要用高频噪声或粗糙度贴图掩盖错误拓扑。
- 纹理分辨率和压缩格式由测量预算决定，不先全量 2K。

### 6.3 灯光/镜头

- 统一主光、环境补光和轮廓光。
- 阴影优先服务于设备可读性；远景小件不默认投影。
- 透明壳体、液层、气相和粒子分别制定深度写入/排序规则。
- 每个 Hero 提供 overview、front、side、45°、cutaway、detail 验收视图。
- 相机不得进入关键设备内部；镜头移动遵守 reduced-motion 设置。

## 7. 细节等级、结构状态与性能

### 7.1 细节等级与结构状态分离

不再使用含义容易混淆的 LOD0/LOD1/LOD2 作为主要业务字段。Manifest 和运行时采用：

- `detailLevel`: `overview / detail / closeup`；
- `structureMode`: `external / half / full / ghost`；
- `animationMode`: `idle / running / paused`。

如底层 Three.js 仍使用 `THREE.LOD`，应在适配层把上述语义映射为距离阈值；不得让渲染 LOD 与剖切模式耦合。

### 7.2 加载策略

- 首屏只加载总览必需资产。
- 进入环节加载该环节 detail 表示。
- 用户打开剖切或特写再加载 closeup/内部节点。
- 资源缓存设置上限、引用计数和统一 dispose。
- 同一 assetId 重复进入关卡不得重复创建同一 Geometry/Material/Texture。

### 7.3 性能指标口径

A. **运行时资源计数（不是显存字节数）**：

- `renderer.info.render.calls`、`triangles`；
- `renderer.info.memory.geometries`、`textures`；
- program 数量、资源加载/解析耗时。

B. **资产侧字节估算**：

- GLB 下载字节数；
- position/normal/uv/index BufferAttribute 字节数；
- 贴图解码尺寸和 mipmap 粗略估算；
- 必须标记为 estimate，不得称为真实 VRAM。

C. **设备侧实测**：

- 只有目标设备、浏览器、驱动/系统提供可靠观测时，才报告 GPU 显存实际占用。
- 不可观测时明确写“无法从当前浏览器可靠读取真实 VRAM”，不得用 Three.js 资源计数替代。

### 7.4 测量协议

每次性能测试固定并记录：设备/GPU/驱动、操作系统、浏览器版本、窗口大小/DPR、场景、镜头、动画状态、资产版本、预热时长、采样时长。至少报告 FPS 平均值、P5、frame time P95、draw calls、triangles、geometry/texture 计数、首帧可见时间和资源加载失败。

候选性能目标：桌面常规场景目标稳定 45 FPS，30 FPS 为最低参考；低于 30 FPS 持续 3 秒触发降级。该门槛是待目标设备基线校准的候选值，不得在未实测时作为通过标准。

降级恢复采用滞回：进入低档后需在更高帧率区间持续一段稳定窗口再恢复，并设置冷却时间，避免画质频繁抖动。建议初始策略为低于 30 FPS 连续 3 秒降级，恢复需高于 45 FPS 连续 10 秒，两个切换动作之间至少冷却 10 秒；上线前用目标设备验证。

### 7.5 降级顺序

1. 降低 DPR；
2. 关闭远景/非关键粒子；
3. 降低阴影质量或关闭远景阴影；
4. 切换 detailLevel；
5. 降低透明叠层和后处理成本；
6. 暂停非当前区域动画。

不得通过隐藏核心设备、删掉关键物流或改变工艺逻辑获得 FPS。

### 7.6 资源释放

`dispose()` 应覆盖 Geometry、Material、Texture、ImageBitmap、AnimationMixer、事件监听和 WebGL 相关资源。共享资源采用引用计数/明确所有权，避免关卡释放时误删共享资源。重复进出 L1–L5 至少 10 轮，资源计数不应持续单调增长。

- 当前测试命令、可用工具、缺失工具；
- L3 70% 业务规则与重置规则单独记录。

门禁：没有完成只读盘点，不进入写代码阶段。

### Phase 1：资产契约和 Schema（P0）

交付：
- `docs/model-contract.md`；
- `schemas/asset-manifest.schema.json`；
- Blender 自定义属性命名约定；
- `nodeUid` 生成/持久化/重复检查工具；
- glTF extras 与 Manifest 一致性检查器；
- 一份真实已有资产的试点 Manifest。

门禁：试点资产的节点身份可追踪、唯一、导出后不丢失。未通过不建新资产。

### Phase 2：L4 语义清单和对象归属（P0）

交付：
- 当前 tower 资产完整 node inventory；
- `tower` Manifest；
- `make_tower.py` 稳定 ID 与非交互支撑处理；
- `l4.js` 显式映射替换正则权威分组；
- `tower.html` 与 L4 共用同一 Manifest。

门禁：节点归属全部可解释，未知节点为 0 或有明确 support 记录；设备选择无错组。

### Phase 3：连接 Schema 与单一路径垂直切片（P0）

交付：
- `schemas/process-connections.schema.json`；
- `web/data/process-connections.json`；
- Blender 读取 JSON 生成实体管线的能力；
- 前端 ConnectionRenderer/FlowAnimator 读取同一连接数据；
- 一条已有且工艺依据已批准的连接垂直切片。

推荐优先审查 L4 常压塔顶气相至冷凝器连接；若仓库工艺资料不能证明其状态为 approved，则不得自行创建生产路径，改为完成 schema/anchor/构建管线机制的开发态验证，并将该连接标注 draft、阻断正式发布。可在依据确认后补齐。

强制验收：只修改一个 waypoint，重新构建后 Blender 实体管线和前端显示/粒子路线同时变化。

门禁：数据单一来源被实测证明，anchor 端点误差通过，工艺依据状态符合发布规则。

### Phase 4：L2 三态真实剖切（P0）

交付：
- 分离器真实剖切资产检查/修复；
- external/half/ghost 状态机；
- L2 状态恢复与 E2E 测试；
- 新截图和 Manifest。

门禁：half 必须显示实际剖切壳/切面；连续切换和退出重进无状态污染。

### Phase 5：自动化校验和证据基线（P0）

测试技术选择：
- Schema/Manifest：Node.js + AJV；
- 浏览器交互 E2E：Playwright；
- Blender 构建：项目实际 Blender 版本的 headless 命令；
- WebGL CI smoke：Chromium + 软件 WebGL 仅用于功能冒烟，不用于性能通过判定；
- 视觉回归：截图与人工核验结合，不以图像相似度取代结构断言。

交付：`npm run validate:assets`、`npm run test:e2e`（或仓库实际命名）及证据输出目录。

门禁：所有 P0 断言通过；无法运行的测试明确列出 blocker，不得报为通过。

### Phase 6：GLB Loader（P1）

先核实旧运行时，再引入精确版本 three + esbuild + GLTFLoader 单 bundle，完成单资产试点、fallback、资源释放后再逐资产迁移。不得一次性全量替换。

### Phase 7：L3 储罐和泵组 Hero（P1）

先资产建模，再替换近景程序化罐体；保持 70% 业务完成、泵送可选、每次进入重置 2% 的逻辑。

### Phase 8：L5 产品/材料/制品/应用场景（P1）

先完成数据模型和分类逻辑，再逐个替换基础几何体。先做能代表类别的高价值资产，不追求一次性全量精模。

### Phase 9：L1 地质/井筒精修（P2）

复用现有 Hero，改善地层断面、微观孔隙、井筒结构和语义锚点。

### Phase 10：全局 PBR、细节等级和性能调优（P2）

在资产语义和加载体系稳定后，建立统一材质、灯光、视角、LOD/表示层级和真实设备性能基线。

## 10. 自动化验收矩阵

### 10.1 资产与 Schema

- [ ] 所有资产均有可追踪的源文件、构建器、版本、提交 SHA 和导出参数。
- [ ] nodeUid 不为空、不重复，且重建后稳定。
- [ ] glTF extras 与 Manifest 核心字段一致。
- [ ] 所有对象/系统/语义节点/锚点引用存在。
- [ ] 未登记节点必须被列入 `nonInteractiveSupport`，未知节点为 0。
- [ ] GLB hash、大小、节点数、Mesh 数、三角面数、材质和贴图统计自动生成。
- [ ] 第三方资产、纹理、字体和 HDRI 有来源/许可记录。

### 10.2 工艺连接

- [ ] Connection JSON 符合 Schema。
- [ ] from/to anchor 存在，且 owner object 匹配。
- [ ] waypoints 坐标空间明确；不允许裸坐标。
- [ ] Blender 构建和前端路径都读取同一 JSON。
- [ ] 一个 waypoint 变化能同步改变实体管线与前端路径。
- [ ] 端点位置/方向误差满足经校准的容差。
- [ ] `draft/rejected` 连接不进入正式发布。
- [ ] 物流动画方向与 connection `direction` 一致。

### 10.3 L2/L3/L4 交互

| 场景 | 操作 | 关键断言 |
|---|---|---|
| L2 | external→half→ghost→external，多次切换 | half 有真实切面；ghost 是透明壳；没有残留透明/隐藏状态 |
| L2 | 选择气/油/水出口，重置和退出 | 对应 object/connection 正确，状态恢复 |
| L3 任务 | 液位从 2% 拖至 70% | 任务完成，不要求泵送和双罐观察 |
| L3 模型 | 液位 10/50/90%，两种罐型切换 | 油面正确，浮盘跟随，固定顶不动，状态互不污染 |
| L3 可选泵送 | 启动/暂停/重播 | 粒子沿统一 connection，端点匹配总览 |
| L3 重进 | 退出后重进、任务重置 | 液位回到 2%，泵停止，完成态清除，默认固定顶罐 |
| L4 | 逐个选塔/加热炉/汽提塔/冷凝器/回流罐 | 分组无错，无遗漏，无未知未解释节点 |
| L4 | 外观/半剖/全剖，馏分路径切换 | 结构模式正确；物流按 approved 连接展示 |
| 全局 | 连续进入退出 L1–L5 至少 10 轮 | 无持续资源增长、无事件监听重复、无 WebGL error |

### 10.4 性能测试

- CI WebGL smoke 只验证功能，不作为显卡性能结果。
- 实机测试需有设备、GPU、驱动、浏览器、视口、DPR、资产版本和测试时间。
- FPS 报告平均值/P5，frame time P95；记录 draw calls/triangles/resource counts/加载字节/首帧时间。
- 真实 VRAM 无可靠读取时明确标注不可得；不得把资源数量写成显存。
- 未执行实机测试的项目状态为 `NOT_MEASURED`，不是 `PASS`。

## 11. 交付物与完成定义

每个资产至少交付：

1. 可编辑 Blender 源文件；
2. 网页运行 GLB；
3. Manifest 和 Schema 校验结果；
4. 稳定 ID、锚点、系统/设备/语义映射；
5. 构建日志、Blender/导出器版本、构建脚本 commit、hash；
6. overview/front/side/45°/cutaway/detail 截图；
7. 实际网页加载截图或录屏；
8. 对应 E2E 报告与控制台日志；
9. 性能数据（仅限已在目标设备测量的部分）；
10. 工艺依据及审批记录。

一个阶段只有在代码、资产、浏览器实际运行、自动断言和证据齐全后才可标为完成。仅“脚本执行成功”“Blender 能打开”或“截图看起来正常”不构成验收通过。

## 12. 推荐实际执行顺序

1. Phase 0：只读冻结基线，确认 Harness 工作区和工具状态。
2. Phase 1：资产契约、Manifest Schema、nodeUid 和检查器。
3. Phase 2：L4 全量对象清点和语义映射。
4. Phase 3：Connection Schema + 一条经过工艺依据审查的垂直切片。
5. Phase 4：L2 external/half/ghost 三态真实剖切。
6. Phase 5：Playwright/Schema/Blender 自动化验收与证据。
7. Phase 6：esbuild + GLTFLoader 单资产试点，建立统一 ModelLoader。
8. Phase 7：L3 储罐与转输泵组资产迁移。
9. Phase 8：L5 产品/材料/制品/应用场景资产。
10. Phase 9：L1 地质和井筒精修。
11. Phase 10：全局 PBR、表示层级、性能基线和自适应降级。

**严格按顺序执行。** 除非用户明确要求，不允许将两个阶段合并成一个大型 Prompt。每一阶段必须先通过自己的门禁，再运行下一阶段。

## 14. 最终决策

先把资产身份、工艺连接和验收基础做对，再扩建模型。首个目标不是让画面更复杂，而是做到：

- 任意一个可交互设备/部件在 Blender、GLB、Manifest、Three.js 和场景上下文中都能被唯一定位；
- 任意一条教学物流能追溯到连接 ID、端点锚点和审核依据；
- 实体管线和前端动画读取同一条连接数据，改一次数据同步变化；
- L2 半剖真实，L3 任务规则不回退，L4 设备不串组；
- 每个阶段都能自动测试、复现并提交证据。

达到这些条件后，再持续投入储罐、泵组、产品、地质微观细节和全局视觉升级，才不会把模型资产越做越多、系统却越来越难维护。
